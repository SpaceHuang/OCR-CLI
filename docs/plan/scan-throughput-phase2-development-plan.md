## 0. 现状与问题定位

### 0.1 一期落点（当前 main，二期对照基线）

| 模式 | 墙钟（金集 30 页） | 解码聚合 tok/s | 相对 P0 |
|---|---:|---:|---:|
| P0 单流基线（Vulkan） | 54.9–55.8 s | 283 | 1.00× |
| **批深 4（Vulkan，合并后复验）** | **40.0 s** | **424** | **1.38×** |
| 批深 4（CUDA） | 42.9 s | 388 | 1.28× |

批深 4 墙钟分解（Vulkan，12 839 token）：**解码段 ≈30.3 s**（12 839 ÷ 424）+ **非解码段 ≈9.7 s**。

### 0.2 解码段缺口：每步 host 路径 ≈5.6 ms

- 集成每步耗时：4 / 424 = **9.43 ms/step**（窗口 4 序列并行前进一步）。
- 隔离参照（R0.6 batched-bench，同源修订 `9e3b928`，warm）：B=4 = **1030.7 tok/s → 3.88 ms/step**。
- **缺口 ≈5.6 ms/step**。若全兑现，解码段下界 ≈ 12 839 ÷ 1030 ≈ **12.5 s**（另含 mmproj 图像编码份额，见 T0.1 拆分）。

### 0.3 已排除与待拆分

- **已排除（2026-11-03 诊断）**：窗口 n_ctx 规模不是缺口来源——batched-bench @B=4 在 n_ctx 35840 与 73728 两点均 ≈1040 tok/s（漂移 <1%）。原始数据由 T0.2 归档。
- **待拆分（T0.1）**：① 每步 `LlamaBatch::new` 构建（N 序列的 token/pos 数组分配与填充）；② 逐槽 FFI 调用（`get_logits_ith`、采样、detokenize，每步 ×N 槽）；③ 逐槽环检测/终止判断（K=256 环窗）；④ mmproj 图像编码份额（页级固定 ≈142 ms 中的编码部分，属 GPU 工作量，host 优化不可消除）。
- **前车之鉴**：一期 T2.2 单流路径 batch 复用实测仅 0.8%（<2% 规则回滚，`e5c8a5f`）——单流包装层附加仅 ≈+0.17 ms/token。二期对象是**窗口路径每步 N 序列构建**，量级不同，不可用一期单流结论外推，但同样**必须先拆分后动手**（T0.1 是阶段 A 的前置门）。

## 2. 规则（沿用一期，全阶段有效）

1. **收益判定**：wall 改善 <2% 且实现更复杂 → 回滚；一般采纳线 ≥2%；A/C 两个高投入阶段建议 ≥5% 才合入（合入前以独立提交逐项判定）。
2. **性能冻结必须在正确性验证通过的构建上采集**（一期 v1 坏管线数据作废教训）。任何窗口解码循环改动，先过真实模型 gated 回归（窗口输出 == 单流输出逐字节，`multi_sequence_spike.rs` / `real_model_window_decode_matches_single_stream_prefix`），再跑性能。
3. **门禁分档**：

   | 档 | 适用 | 内容 |
   |---|---|---|
   | 第一档（逐字节） | A、X1（语义中性改动） | 金集 `document.md`/`page-*` 与 `a02d459` 冻结参照逐字节一致（Vulkan + CUDA 双后端） |
   | 第二档（相似度） | C、D（批组合/权重变化） | 结构化相似度 ≥0.999 vs 单流参照 + 人工抽检 |
   | 自一致性 | 全部 | 同输入同配置连跑两遍，**内容产物集合**（`document.md` + 非计时 `page-*`）逐字节相同；`result.json`/`gpu-resource.json` 走结构化比较（排除 `elapsed_ms` 等计时字段，路径字段按预期布局比较）——MAJOR-1 修正口径，沿用 P0 既定口径 |

4. **双口径纪律**：隔离 bench 上界 ≠ 集成兑现；兑现率以实测定，不按 bench 曲线线性外推做承诺（N=4 兑现率实测 ≈47%：bench 预测 3.21×，集成 1.52×）。
5. **计时卫生**：warm 复测（Vulkan 冷启动首遍 shader 编译污染，R0.6 教训）；Vulkan/CUDA **独占重验**（禁止双链并行，一期 v3 竞争污染 17 s 教训）；每项结论两遍 <2%。
6. **输入钉定**：金集 `source.pdf` sha256 `5d7adf7d…` 不变；新增多文档 fixture 同规则管理（不随仓库分发，untracked + 重建脚本，参照 `assemble-regression-pdf.py` 模式）。
7. **工程卫生**：`cargo fmt`/`clippy --workspace --all-targets` 零警告、`cargo test --workspace` 全绿；Windows 构建配方沿用一期 §5.5（Ninja + vcvars64 + 短 `CARGO_TARGET_DIR` + LNK 文件锁重试）。

### 阶段 B1：模型校验缓存（v1.1 裁决：不实施）

评审 BLK-1 判定原设计逻辑互斥：sidecar 键（revision+path+size+mtime）命中即跳过 SHA-256，则"同 size 同 mtime 的内容篡改必须检出"（原 B1.4 墓碑验收）不可能成立——命中路径既无内容比对、也无"键异常 → 回退全量"的触发条件；该改动亦不属语义中性（原归第一档为错误分类）。三承诺——跨进程持久缓存、scan 完整性等价、同元数据篡改必检出——最多同时保二。

**裁决**：采纳评审建议，保完整性契约。scan 默认路径维持每次全量 SHA-256（`verify_manifest_files` 行为与契约不变，`ocrx-models/src/lib.rs:394`）；跨进程缓存方案撤销；`ocrx model verify` 全量校验通道本就存在，无需新增。后果与去向：

- 单文档固定税中 sha256 部分（≈1–4 s）保留，**不作为本期杠杆**；v1.0 中依赖 B1 的 −2~4 s 收益与 M3 里程碑撤回（§5）。
- 多文档场景的固定税摊薄不依赖缓存：X1 单调用内校验+加载本就只发生一次，收益自动并入 X1。
- sidecar 的原子写入、失效规则等工程项随之作废；若未来立项"放宽完整性契约"（opt-in 快速档 + `ocrx model verify` 全量校验），另走独立提案评审。

| X1.0 | 半页设计小文档（**其中 PDFium 协议冻结为 X1.1/X1.2 的前置评审门禁**）：CLI 面（`ocrx scan a.pdf b.pdf dir/ -o <output-root>`，多输入 + 目录展开 + 去重 + 不存在即失败 exit 2）、编排器（共享 actor 的文档级窗口 FIFO：下一个窗口只从当前队首文档取页）、逐文档进度（日志 doc 前缀）、退出码聚合（任一文档失败 → 非零 + 汇总，失败文档不影响其余）、取消 = 整调用（Ctrl-C → 所有在飞窗口零提交，机制 A 语义自然成立）。**PDFium 协议（BLK-2）**：① 整调用唯一 owner 线程——延续一期 §6.1–6.2 不变式；每文档各自 `spawn` 被禁止（进程全局 `OnceLock` 绑定的跨线程复用），主线程兜底同样禁止；② 协议新增 `SwitchDocument{input}`（或全部请求携带文档身份），owner 据此切换输入与渲染配置；③ 切换仅允许在无在飞渲染的窗口调度边界（编排器串行化），切换时清空预取缓存、重置 `next_prefetch`；④ 文档级错误（不可读 PDF 等）作为值经通道返回、继续后续文档；owner 超时/悬挂/通道断开仍为**整调用 fail-loud**，禁止另起 owner；⑤ 单输入路径零行为变化 |
| X1.1 | `parse_scan_args` 多输入扩展单测：混合位置参数/选项、目录展开、去重、空集报错、`--resume` 按文档独立 |
| X1.2 | 编排器实现：模型加载/校验**一次**（固定税每调用摊薄，BLK-1 裁决后的去向），文档队列 → 窗口调度；`SwitchDocument` 协议实现（owner 状态机：活动文档身份、预取按文档键控或切换即作废）；单文档页级失败继续（沿用页级语义）、文档级致命错误（不可读 PDF）作为值返回并跳过该文档继续其余 |
| X1.3 | 输出布局：`output-root/<doc-stem>-<hash8>/`（碰撞后缀），逐文档 `result.json` + 汇总 `scan-summary.json` |
| X1.4 | 门禁（分组表述，逐字节集合按 §2 修正口径 = `document.md` + 非计时 `page-*`）。**① 内容等价**：多文档各文档内容产物 == 该文档单独扫描输出逐字节（窗口组成按文档独立，确定性成立）；`result.json` 结构化比较——排除 `elapsed_ms`，路径字段（`markdown_path`/`output_dir`/`images.directory`）按 X1.3 布局各自预期值比较，`gpu-resource.json` 只比较非计时字段（MAJOR-1）。**② 单输入兼容**：默认单输入命令行为不变，单独门禁，不与①混写；金集单文档复测不回退。**③ 安全验收（BLK-2）**：两文档顺序处理全程同一 owner 线程（线程 id 断言）；第二文档零命中第一文档的页缓存/预取（沿 `inject_render_failure` seam 扩展断言）；不可读第二文档作为文档级错误跳过且后续文档继续；owner 超时注入 → 整调用终止，且无第二 owner 线程、无主线程 PDFium 调用。**④ 场景**：`md-small-20` ≥1.5× |

**落档**：`docs/develop/cross-doc-orchestration-<date>.md`。

### 决策点：X2 / B2 / D（各 ≈0.5–1 天 spike，输出决策文档，不预设合入）

- **X2 跨文档混窗**：小文档欠填充的量化收益（`md-mixed` 场景）；取消与批级错误回退（深度 1 整窗重扫会波及他文档页）的语义代价评估。值得 → 走 P4.2 同规格设计评审；不值得 → 记录关闭。
- **B2 常驻进程**：serve/watch 两形态对比；**与 X1 的价值重叠必须显式核算**（X1 已把多文档的加载/校验摊薄到一次，B2 残余价值只剩"重复单次调用"场景）→ 大概率降级或不做。
- **D 推广决策**：基于 T0.4——质量门禁（金集相似度 ≥0.999 + 10 页人工抽检）通过 → 文档化 compact 为快速档（含 `--model-profile compact` 使用指引与质量提示）；不通过 → 记录数据不推广；顺带评估四档 profile 推荐链是否更新（reference 仍为默认，compact 保持 opt-in）。

## 5. 累计预期与里程碑

| 里程碑 | 内容 | 墙钟（现实目标） | 墙钟（上界） |
|---|---|---:|---:|
| M0 | 现状 `a02d459` | 40.0 s | — |
| M1 | +A（host-path） | ≤32 s | ≈23–26 s |
| M2 | +C（批深 8）＝**单文档终线** | ≤27 s | ≈20–22 s |

- B1 撤销（BLK-1）后，单文档现实终线 = M2；主目标 ≤26 s 取 A+C 现实区间（≈24–27 s）的中值；v1.0 的 23–25 s 带（依赖 B1）撤回。
- 上界仅在 T0.1 证实 host 份额占缺口 ≥80% 时才作为承诺线；现实线是本计划的主目标口径。
- M2 达成即 ≈**2.05–2.2× vs P0（55.5 s）**，冲刺 ≤22 s ≈2.5×；CUDA 后端按同门禁复测（收益构成与 Vulkan 不同，须独立实测，一期 §7.2 原则）。
- X 场景收益单列（多文档，含固定税每调用摊薄一次），不计入单文档口径。

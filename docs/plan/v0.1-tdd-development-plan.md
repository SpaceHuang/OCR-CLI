## 1. 目标、边界与完成准则

本计划将技术方案落地为 `ocrx` v0.1 的可测试 Rust CLI。实现顺序严格采用测试先行（Red → Green → Refactor）：每个工作项先提交失败的测试或 golden fixture，再写最小实现使其通过，最后只做不改变外部契约的重构。

本计划的发布范围仅为技术方案第 1.1 节所定义的内容：macOS 14+ Apple Silicon 上，以进程内 llama.cpp Rust binding/libmtmd 运行唯一模型 `ovisocr2`，完成 PDF 逐页 OCR、Markdown/PNG 输出、checkpoint 恢复、模型管理、诊断、Skill、安装与验证。

下列事项明确不排入任何迭代、测试 fixture、命令或隐藏开关：GUI、云 OCR、训练/微调、第二模型、动态 adapter/模型注册、页面并发、跨文档合并、OCR 文本层回写、`ocrx clean`、语义图片命名/alt text、pipe table、遥测、Linux/Windows 正式工件以及未在需求中列出的命令参数。技术方案中为后续平台保留的描述不得转化为本计划的开发或发布任务；macOS 以外只能保留为不执行的兼容性边界测试。

完成定义：只有技术方案第 17 节的 macOS 范围内条件全部有可复现证据，且所有自动化门禁、真实模型 E2E、质量基准、资源报告、安装包烟测均通过，才标记 v0.1 完成。任何 P0 硬门禁失败均停止进入相应后续实现阶段，而不是以降级功能绕过。

## 3. 通用 TDD 与工程规则

### 3.1 测试组织

每个 crate 使用单元测试覆盖纯逻辑；跨 crate 的稳定 JSON、Markdown 和 CLI 文本使用 golden；文件系统、子进程、下载与 runtime 使用组件/集成测试。真实模型测试必须与 fake runtime 测试分层，默认单元和契约测试不得联网、不得需要模型权重或人工输入。

建议目录约定：

```text
src/<crate>/src/
src/<crate>/tests/
src/<crate>/tests/fixtures/
tests/cli/
tests/integration/
tests/support/
benchmarks/{manifest,truth,results,reports}/
assets/{manifests/ovisocr2/<revision>,skills/ocrx}/
```

fixture 必须版本化、可追溯且离线可运行。任何真实 PDF/模型因许可证无法提交时，提交清单、SHA-256、获取/授权说明和跳过条件；测试报告不得把跳过写成通过。

### 3.2 每项工作的固定循环

1. 在任务说明中列出涉及的需求章节、输入、预期输出、退出码和非目标。
2. 新增一个最小失败测试（或先更新 golden 使之失败）；先确认其因待实现行为失败，而非测试环境错误。
3. 仅实现让测试通过的最小生产代码；禁止顺手增加未计划参数、模型、平台分支或输出字段。
4. 执行相关 crate 测试、workspace 格式化/lint 与受影响集成测试。
5. 在行为稳定后重构，重跑同一测试集合；若稳定 JSON/CLI 输出变化，必须先更新版本策略并评审，v0.1 内不得悄然改名或改类型。
6. 在计划勾选项中记录测试名、命令、结果与证据路径。

### 3.3 每个合并点的最低门禁

- `cargo fmt --all -- --check`；
- `cargo test --workspace`（真实模型标记测试可按显式环境变量运行）；
- 受影响 crate 的 Clippy，新增 warning 不得引入；
- 无网络单元/契约测试；
- 对 CLI/JSON 改动执行 stdout/stderr 捕获测试；
- 对文件输出改动执行临时文件、原子 rename 与路径逃逸测试。

                      ├→ P1 领域契约与 CLI 外壳 → P2 配置/模型事务 ─┐
PDF worker 冻结 ──────┘                                               │
                                                                      ├→ P3 fake 全流水线 → P4 真实 runtime/PDF/输出恢复

### P0.2 回归集与评分器

- Red：为至少 30 页人工真值集建立 manifest/schema 测试，缺少任一规定场景、少于两页类别覆盖、缺真值字段或基准元数据即失败。

- 验收：同一固定假结果重复评分字节级一致；报告包含样本数、逐页结果、模型/runtime/adapter/prompt/基准版本。

### P0.3 真实 runtime 与质量门禁

- Red：用锁定输入建立 `llama-mtmd-cli` 与 Rust binding 的结构化输出比对 golden；增加 EOS、max-token、取消、Metal 初始化失败的预期测试。
- Green：实现或补齐 runtime 探测、加载、MTMD 编码、生成和安全释放，使 Rust 路径达到已冻结的对齐准则。
- Green：在 runtime 冒烟跑通后，从已锁定的真实 PDF 回归输入中选取 2–3 页，保存原始生成输出、finish reason、渲染/送模尺寸和运行时/模型/adapter 元数据，作为仅供契约设计的受控样本。样本必须覆盖至少一个含视觉区域或结构化内容的页面；如真实输出未包含该形状，应如实记录，不得手写或伪造模型输出补齐。

- 验收：reference、quality、compact 和最终 16 GB 默认 profile 满足需求 17.2；上述受控真实输出样本可在 P1.1 使用；生成没有不可控循环、截断或空白失败页。任何未达标结果为 go/no-go 阻断，不能由第二模型或隐藏 fallback 代替。

### P0.4 PDF worker 与资源策略

- Red：补齐 worker 协议测试：空/倒序/越界段、异常退出、超时、取消、缺页、页名错误、PNG 损坏、`.part` 残留及 hash 不符均不得提交页段。
- Green：由主进程按 `[start,end)` 连续半开区间调度默认 20 页的 `pdfium-worker`；worker 只渲染 RGB8/300 DPI 至页段私有临时目录，主进程验证后再提交。
- Green：在多份真实复杂 PDF 和 100 页 fixture 上采集 RSS/footprint、耗时、页段峰值和退出状态，验证 worker 退出回收内容相关 PDFium 缓存。
- Refactor：将 worker IPC/文件协议封装在 `ocrx-pdf`，不泄漏到模型、checkpoint 或 Markdown 层。
- 验收：资源报告证明 100 页处理无随页数线性增长；PDFium 只在 worker 进程内初始化一次；正常、非 PDF、损坏、加密/密码错误、动态库缺失分类稳定。未解决资源上限前，P4 不得宣称扫描流水线完成。

## 13. 变更控制

每个 PR/提交必须关联本计划中的一个阶段和具体测试。若需求、技术方案、manifest revision、runtime 组合、模型权重、prompt/schema、评分器或 fixture 发生变化：先更新相应冻结记录与测试，再将基准版本递增并全量重跑受影响质量/兼容性证据。不得将未验证的候选数据写成发布承诺。

发现以下任一情况应停止当前实施并记录阻断，而不是自行扩展设计：需要第二模型/CPU fallback/并发才能通过；模型来源或再分发资格不清；P0 质量不达标；PDF worker 无法满足资源门禁；需求与技术方案对首发平台或安装脚本形成实质冲突。恢复工作前应由产品/技术方案明确更新范围和验收条件。

## 1. 交付内容

- **`CommitProfile` 类型**（`ocrx-output/src/commit_profile.rs`）：逐页 `{page, generation, render_wait_us, owner_render_us, png_encode_us, commit_write_us}` + 终态 totals + `finalize_us`；`schema_version:1` 黄金串锁定（含空 profile 形状）。generation 键控——每次渲染 attempt 一行，`mark_terminal` 只折叠终态 attempt（退化重试/回退的全部 attempt 均入记录）。runtime `StepProfile` 一字未动（v1.1 BLK-2 延续）。
- **`CommitRecorder`**：`OCRX_STEP_PROFILE` 同开关 env-gated；`Arc<Mutex>` 共享，disabled 全 no-op。
- **采集链**（v2.1 BLK-4 冻结口径）：
  - `render_wait_us`：三个渲染调用点（serial 含扰动重试、batched 循环）调用者侧墙钟；
  - `owner_render_us`：`PdfResponse::Render` 改携 `(RenderedPage, u64)`，owner 线程在 `render_page`/`render_direct` 内计时，prefetch 耗时经 per-page map 随 cache 命中回传，handle 上 stash/take；**仅诊断，不入墙钟闭合**；
  - `png_encode_us`：CLI 识别器两处编码块经共享 recorder sink 回传（不等 P1）；
  - `commit_write_us`：两条提交路径包裹 `commit_page`；`mark_terminal` 覆盖 Committed/RenderFailed/RecognizeFailed 三终态；
  - `finalize_us`：merge+cleanup 一次性记录。
- **落盘**：`commit-profile.json` 每文档 root 一份，与 `step-profile.json` 同点写入；守卫 = env 开 + `!cancelled` + `failed_pages==0` + 快照存在（取消/失败零写盘）。
- **测试**（workspace 395 passed / 0 failed，+8）：recorder 单测 4（黄金串、generation 键控、disabled no-op、克隆共享态）+ e2e 3（各段非空经共享 sink、disabled → `commit_profile()=None`、取消扫描零终态零 finalize）。

## 2. T1.4 实测（RTX 4090 D，Vulkan，release 插桩构建）

数据：`docs/test/reports/phase3-t1-2026-11-05-data/`（金集 + md-small-20 逐文档 20 份 profile）。

### 金集（30 页输入 → native 1 + OCR 27 + empty 2，elapsed 28.56 s）

| 段 | 实测 | 占比 |
|---|---:|---:|
| window decode（step-profile） | 21.21 s | 74.3% |
| **render_wait**（27 页，≈55–75 ms/页） | **1.50 s** | 5.3% |
| residual | 5.28 s | 18.5% |
| png_encode（27 页，≈7–21 ms/页） | 0.40 s | 1.4% |
| commit_write | 0.16 s | 0.6% |
| finalize | 0.01 s | <0.1% |

**墙钟闭合**：render_wait + encode + write + finalize + decode = 23.28 s；residual 5.28 s ≈ 二期账本"校验+加载固定税 ≈5.3 s"（reference 1.5 GB SHA-256 + 模型加载）——**闭合成立**（固定税为运行级成本，不在 commit-profile 范围；±5% 判定按"分项和 + 已知固定税 vs 总墙钟"通过）。

### md-small-20 编排（20×2 页，编排墙钟 ≈18.5 s）

| 段 | 每文档均值 | 20 文档合计 |
|---|---:|---:|
| render_wait（≈155 ms，≈owner_render——demand 渲染主导） | 0.155 s | 3.10 s |
| png_encode | 0.018 s | 0.36 s |
| commit_write | 0.010 s | 0.20 s |
| finalize | 0.002 s | 0.04 s |
| **提交段合计** | **0.185 s** | **3.70 s** |

每文档编排份额 ≈0.185 / 0.93 ≈ **19.9%**；行级证据：页 1 为 demand 渲染（owner ≈65 ms），页 2 走 K=2 预取（owner ≈20 ms，render_wait 涵盖等待）。

## 4. 观察与修正

1. **S0.4 附带结论修正**：T1 构建（pins 0.1.152）金集 28.56 s vs S0.4 构建（0.1.161）30.07–30.87 s——同代码同机下 **0.1.161 慢 ≈2.3 s**。S0.4 报告"升级 −9.4%"的对比基数（34.02 s）是二期**整改前**构建，对比不成立。修正：pins 升级提案**不再有性能论据**，仅存"解除未来绑定能力"论据；若推进须按 WP.2 重审纪律独立提案（工程成本已由 spike 清零）。BS NO-GO 裁决不受影响（其依据是同构建 A/B）。
2. **`render_wait_us` ≈ `owner_render_us`**（md20 0.155 ≈ 0.155）：demand 页 owner 工作完全暴露在调用者等待中；预取命中的页 owner 时间小（20 ms）而 render_wait 仍涵盖其排队。R 输入取 `render_wait_us`（冻结口径）不受影响。
3. 金集 encode ≈7–21 ms/页（二期整改后已远低于 v1.0 估计的 1.5–2 s/页——校准结论再次确认）。
